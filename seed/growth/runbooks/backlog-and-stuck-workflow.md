# 专用手册：消息积压与工作流卡单

本手册处理「有延迟、但还没进死信」的那一类问题：Kafka 消费 lag、UMP 分片堆积、工作流实例停在等待态。死信消息的处置见《用户事件消费链失败消息处置》。

来源：`tradepass.growth/docs/runbooks/workflow-user-event-consumer-dlq.md` 的位点与阻塞重试口径；UMP 分片字段口径见本仓 UMP 的投递场景说明。

## 1. 先分清三种「积压」

| 类型 | 看什么 | 含义 |
|---|---|---|
| 消费 lag | Kafka 每分区的「最新位点 − 消费位点」 | 消息到了还没被消费 |
| 业务待处理量 | 工作流实例停在 `Active` / `Suspended`、UMP 分片停在 `Pending` / `Leased` | 消息已被消费，业务还没推进完 |
| 死信堆积 | `{用户事件}.dlq` 的到达量 | 消费失败已经落盘，不属于「延迟」 |

三者要分开统计，不要合成一个「积压」数：处置动作完全不同。

## 2. Kafka 消费 lag 的判读

- 三条用户事件链各有一个原生消费组（组名带 `.native`），与 CAP 的 `{前缀}.{链名}.v1` 不是同一组；混组会互抢分区、反复再均衡。
- **全组位点一起不动**：消费进程没在跑、订阅面缺失（启动日志里「N 个订阅 topic 还不存在」）、或 broker 不可用。先查进程心跳与日志，不要先去调分区数。
- **lag 匀速上涨**：单分区阻塞（可恢复故障的重试最多约 15 秒，分区内严格串行）或下游写入慢。看同一时刻 MySQL / StarRocks 的错误率。
- **lag 阶梯式上涨后回落**：批量补数或上游突发流量，确认在追即可。
- 加实例不会降低单分区串行链路的延迟。要降延迟只能加分区，而改分区数会影响键序与再均衡，需要单独评估。

### 判定口径

- 15 分钟窗口内三组 lag 的最大值 < 10000 条为健康；
- 持续 > 15 分钟才告警：短时突发的波峰不告警，避免刷屏；
- lag 长期贴近阈值而流量没有增长时，优先查消费侧处理速度，不要放宽阈值。

## 3. 工作流卡单

- 卡单的判据：`wf_instance` 状态是 `Active` / `Suspended`，且入口时间已超过 30 分钟。`wf_instance` 不存「当前节点」，实例位置由轨迹的最后一条进入行现推，确认卡在哪一步要读轨迹。
- 卡单不等于「正在重试」：重试会推进轨迹与重试计数，长时间没有任何推进才是卡单。
- 常见原因：
  1. 等事件丢失（对应死信里有该客户的消息）；
  2. 规则触发没被消费（lag 不动）；
  3. 图级中断短路终止后回写没落地（终态回写走 CAP 内部管道，看 `cap.received`）；
  4. 下游读口（客户画像 / 团队目录）超时，条件求值拿不到字段。
- 恢复后不要手工改实例状态：按补投、重放或让超时窗口自然收尾处置，改状态会破坏去重键与终态语义。

### 判定口径

- 窗口 30 分钟内 `Suspended` 且入口超过 30 分钟的实例数 ≤ 0 为健康；
- 超过阈值先人工确认是否为长等待流程，确认卡死再按 `Critical` 升级；
- 升级前把实例号、客户键、最后一条轨迹时间记进日报备注。

## 4. 任务卡死残留

- 进程内任务（自动化重试任务、工作流定时任务）停在 `Running` 且超过 30 分钟没有心跳，记为残留。
- 先确认对应进程确实不在了，再清理；还在跑的进程与人工清理抢同一批数据会写出重复记录。
- 应用启动时的遗留清理只覆盖本进程创建的残留，跨进程残留需要人工确认。
- v1 用 mock 指标 `worker_stuck_task_total` 表达这个量；接入真实数据源后换成对应任务表的 SQL，判据不变。

### 判定口径

- 30 分钟窗口内残留任务数 ≤ 0 为健康；
- 残留数 > 0 先按 `Warning` 进日报，确认是崩溃残留再升级。

## 5. UMP 分片与发件器

- 分片状态：`Pending`（可抢）、`Leased`（已抢到、租约内）、`Processing`（处理中）、`Completed`、`DeadLetter`。
- 可抢的分片是 `Pending`，或 `Leased` / `Processing` 且 `leased_until` 已过；`next_visible_at` 未到的不抢。因此「Pending 且 `next_visible_at` 已过 10 分钟还没被抢」说明 worker 没在抢片，而不是表里有积压。
- 分片重试到 `max_retry_count`（5）后进 `DeadLetter`，不再调度；分片死信不是 Kafka 死信，处置顺序见对应投递场景说明。
- 发件器按 `published_seq` / `committed_seq` 推进：同一分片 `published_seq = committed_seq` 表示发送侧事件已全部发出。终态分片（`Completed` / `DeadLetter`）仍有 `published_seq < committed_seq` 说明发件器停滞，Kafka 恢复后会自动补发。
- 发件器只读主库；失败一律按瞬时处理、退避重试，不跳过、不放弃。所以「发件器滞后」的根因通常在 Kafka 或主库，不在发件器自身。

### 判定口径

- `Pending` 且 `next_visible_at` 已过 10 分钟的分片数 ≤ 0 为健康；
- 终态分片 `published_seq < committed_seq` 的条数 ≤ 0 为健康；
- 两条都按 `Warning` 进日报，连续 3 个窗口不恢复升级。

## 6. 处置顺序

1. 确认进程都在（心跳）；
2. 确认依赖都通（MySQL / Redis / Kafka / StarRocks）；
3. 区分 lag 还是业务待处理量，按上表选路径；
4. 死信按死信手册处置，不要用「重放整段历史」代替定点补投；
5. 处置完成后观察一个完整窗口再关闭 finding。
