# Growth 通用运维手册

本手册是 Project `growth` 的项目级通用知识（`Kind=General`），自动注入该项目下所有检查单；专用手册按检查单的引用注入。手册只承载知识与口径，不承载可执行判定——判定一律写在检查项的结构化断言里，由框架从工具调用的真实返回复核。

## 1. 服务拓扑

| 进程 | 角色 | 主要职责 | 读写 |
|---|---|---|---|
| `management-svc` | 管理端 API | 页面与后台管理接口、配置读写、运营操作 | MySQL、Redis |
| `openapi-svc` | 开放平台 API | 外部系统回执与 webhook 入口、签名校验、幂等受理 | Kafka、MySQL |
| `growth-worker` | 后台任务 | 工作流实例推进、规则触发、图级中断、等事件投递、CAP 消费 | Kafka、MySQL、Redis |
| `ump-worker` | 统一消息投递 | 抢分片、选路、装配、发送、回执落库、发件器 | MySQL、Kafka，出网到供应商 |
| `materialize-worker` | 物化引擎 | Kafka → StarRocks 流作业、批层校准、DWS 聚合 | Kafka、StarRocks、Redis |
| `callmedia-svc` | 实时语音通话宿主 | SIP 中继、媒体节点、通话状态机 | MySQL、Redis，出网到运营商与媒体 |

数据方向：外部系统 → `openapi-svc` / `management-svc` → Kafka → 各 worker → MySQL / StarRocks；数仓由 `materialize-worker` 从 Kafka 写入，页面与报表读 MySQL / Redis / StarRocks 的产出。

## 2. 依赖与断链症状

| 依赖 | 用途 | 断开后的典型症状 |
|---|---|---|
| MySQL | 业务事实、CAP outbox / inbox、分片与消息状态 | 写入报错、outbox 堆积、任务停在 Running、接口 5xx |
| Redis | 状态、限流与租约、预览缓存 | 抢分片与幂等异常、租约失效、接口延迟升高 |
| Kafka | 事件总线、原生消费组、死信 topic | 消费 lag 上涨、DLQ 堆积、工作流卡单 |
| StarRocks | DWD / DWS 数仓 | 空分区、聚合作业失败、报表与看板空白 |

## 3. 指标与单位口径

### 3.1 命名

- Prometheus 里计数器名字已经带 `_total`，导出时不会重复加后缀；
- 直方图导出后带单位后缀：`gatekeeper_consent_latency_milliseconds_bucket` / `_sum` / `_count`。照代码里的原始名字查直方图会查不到；
- 计数器从未发生过时整条序列不存在。查不到某条失败计数只说明没发生过失败，不代表没接上；判断「接上了没有」看 reach-worker 的进程运行时通用指标是否出现。

### 3.2 单位

- 比例一律用 0–1 小数（`0.2` 表示 20%），阈值与表达式同口径，不要混用百分数；
- 时长：PromQL 用 `5m` / `2m` / `1h` 这类时长字面量；业务侧滞后与等待统一按分钟；
- 数量：条数、人数为整数，窗口内累计用 `increase`，瞬时值用 gauge 直读；
- 时间：库内时间按 UTC 存；调度与日报按 `Asia/Shanghai` 展示，小时级检查单在每小时第 0 分钟触发，日报每天 10:00 生成，执行侧审计默认留存 90 天。

### 3.3 标签

`tenant`（租户）、`hook`（询问 hook 的编号，不是名字）、`outcome`（结果）、`group`（消费组）、`topic`（主题）、`reason`（原因）。

## 4. 断言语义：断言成立 = 健康

- 检查项的 `Operator` + `Threshold` 描述的是**健康条件**，不是故障条件。
- 仓库里的告警表达式大多是**故障条件**，搬进检查项必须取反：

| 告警写法（故障条件） | 健康条件的写法 |
|---|---|
| `increase(x[5m]) > 0` | `x ≤ 0`（`Lte`，阈值 `0`） |
| `max_over_time(x[2m]) == 1` | `x ≤ 0`（`Lte`，阈值 `0`） |
| `失败率 > 0.2` | `失败率 ≤ 0.2`（`Lte`，阈值 `0.2`） |
| `坏数据条数 > 0` | `坏数据条数 ≤ 0`（`Lte`，阈值 `0`） |
| `分区行数 = 0` 表示断链 | `分区行数 > 0`（`Gt`，阈值 `0`） |

- 结构断言是三件套：工具名 + 比较符 + 阈值；再加上参数模板与取值路径，框架才能复核。缺任何一项，复核无法执行，结果落 `Error`，不产生 finding、不发 Lark。
- 没有断言的检查项是信息型：只收集证据，不参与告警。
- 判据变化必须递增 `RuleVersion`，旧 finding 以「判据变更」关闭，新版本重新打开。
- 复核以工具调用的真实返回为准。agent 的 claim 与框架复核不一致时落 `Error`，不建 finding。

## 5. 告警与升级

- 分级：`Critical` 立即通知值班；`Warning` 进日报，同一 finding 连续 3 个调度窗口未恢复升级为 `Critical`；`Info` 只记录。
- 去重：按（项目、环境、检查单、检查项、`RuleVersion`）去重。持续异常只保留一条 finding，不重复通知。
- 通知时机只有三条：finding 打开、恢复、判据变更。恢复通知附持续时长与首次发现时间。
- 静默：判据变更后的一个调度窗口内不重复通知，避免版本切换刷屏。
- v1 的 Lark 通道是 mock，不会真的发出消息。上真通道之前，不要把「收到通知」当作处置完成的标志。

## 6. 排查顺序（固定四步）

1. 服务心跳：六个进程是否都 `healthy`；
2. 依赖连通：MySQL / Redis / Kafka / StarRocks 是否都 `up`；
3. 积压与失败量：Kafka lag、DLQ 到达量、CAP outbox、准入队列、UMP 分片与发件器；
4. 业务表与数仓：工作流卡单、任务残留、空分区、枚举漂移、日量环比、归属对账。

先确认「都活着」，再判断「积压在哪」，最后才看数据内容。顺序反过来容易被表象带偏：心跳正常但依赖断开时，先查依赖；依赖正常但积压上涨时，先查积压来源。

## 7. 止血与补投原则

- 先止血、再补投：根因未消除前补投会再死一次；
- 补投只把原始 value 原样发回源 topic，不套信封、不重新编码；
- 不手工改数仓与业务库数据；对账差异先取证，再决定处置；
- 每次手工操作把时间、范围、操作人写进日报备注，便于事后复盘；
- 不要为了「让检查变绿」放宽阈值或关掉检查项。判据要改就走 `RuleVersion`，并写明理由。

## 8. mock 工具约定（v1）

v1 全链路 mock：检查项通过登记的 mock MCP server（名称 `mock`）取证，工具名格式是 `mock__{工具}`。v1 使用的三个工具：

| 工具名 | 用途 | 返回形状（约定） |
|---|---|---|
| `mock__GetServiceHealth` | 进程心跳、依赖连通 | `{"status": "healthy"}` / `{"status": "up"}`；异常为 `degraded` / `down` |
| `mock__QueryMetric` | 指标聚合取值 | `{"value": <数字>}` |
| `mock__QuerySql` | 只读聚合查询 | 聚合列名由 SQL 决定，如 `{"count": 0}`、`{"rows": 0}` |

- 检查项的 `ValuePath` 必须与返回形状一致。新增工具或改返回形状时，同批改检查项，并递增受影响检查项的 `RuleVersion`。
- 参数模板里的 SQL 与指标名是 v1 mock 口径：接入真实数据源时按数据字典校准表名与列名，判据本身不变，同样递增 `RuleVersion`。
- mock server 实现必须按上表返回，否则断言复核落 `Error`。

## 9. 已知口径差异

- 触达准入的告警条数：任务正文写「5 条」，但同处枚举出 6 条（失败行数、熔断、失败率、SIP 线路、媒体节点、暂停外呼）。本项目按 6 条落地：前 3 条有来源表达式、按判定型落；后 3 条来源手册未给出表达式，按信息型落，拿到定义后再补断言。差异说明见 `docs/inspection-knowledge.md`。
