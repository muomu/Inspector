# 数仓作业重跑

> 口径改了、历史数据留着旧值时，用它把数算回来。**不改声明、不改表、不动 Kafka**——
> 重跑只是拿现有的声明，在你给的窗口上再算一遍。

## 什么时候用它

| 情形 | 用不用 |
|---|---|
| 改了聚合/批作业的口径，历史行还是老值 | ✅ 用 |
| 新加一列，历史客户全是空 | ✅ 用 |
| 上游明细表本身缺行 / 缺列 | ❌ 补不了。明细是流层从事件落的，源头在 Kafka 或生产方 |
| 数据只是有点旧 | ❌ 等常驻 worker 的对账，别抢它的活 |

判据：**这个数算得出来吗**——只要它的输入已经在数仓里，重跑就管用；输入本身缺，重跑跑一万遍也是那个数。

## 怎么跑

重跑与常驻 worker 是**同一个镜像**，差别只在启动参数。K8s 里起一个一次性 Job，
`image` 抄当前负责 metrics-worker 的 StatefulSet（工作负载名以 deploy 仓为准）正在用的那个 tag，
`env` / `envFrom` 原样照抄，`args` 换成下面这些：

```
--rerun
--jobs cst.profile.current_stage,cst.profile.current_stage_rank
--from 2024-01-01
--to   2026-08-01
```

参数：

| 参数 | 说明 |
|---|---|
| `--rerun` | 有它才是重跑模式；没有就是常驻 worker |
| `--jobs a,b,c` | 点名作业 |
| `--jobs-for-table t1,t2` | 按目标表选，写这些表的作业全跑 |
| `--all` | 全部有批层执行路径的作业 |
| `--from` / `--to` | 窗口，**左闭右开**。只给日期按 UTC 零点算 |
| `--mode` | `reconciliation`（默认，逐分区覆写 + 校验）或 `microbatch` |
| `--tenant` | 只跑一个租户；不给就是全部 |
| `--chunk-days` | 每片多少天，默认 30；给 0 表示整段一片 |
| `--dry-run` | 只打印计划，不跑 |
| `--allow-overlap` | 放行与调度回看区间重叠的窗口，见下 |

三种选法互斥。作业名拼错会当场拒，不会静默跑成空。

**先 `--dry-run` 一次**：它会把「跑哪几条、什么顺序、切几片」打出来。顺序按作业声明的
`DependsOn` 拓扑排，上游排在下游前面。

## 退出码

| 码 | 含义 |
|---|---|
| 0 | 全跑完，没有失败 |
| 1 | 至少一片失败。日志里每片一条 error |
| 2 | **一片都没真跑起来**（全被跳过） |
| 3 | **参数不合法，或被重叠守卫拦下。什么都没跑** |

2 与 3 分开是有用的：3 是「你给错了」，改命令重来；2 是「命令没问题但一片都没执行」。

「跑了但没数据可算」是 **0**，不是 2——日志里那条 `写入 0 行` 就是它。跳过指的是作业
根本没有执行路径或被数据质量断言挡住，与「算出来是空」不是一回事。

## 会被拦下的一种情况

窗口止点落进某条作业的**调度回看区间**时，重跑当场拒绝并打印每条作业的回看起点。

原因：常驻 worker 的调度器按声明的节奏也在跑这些作业，两个进程会同时覆写同一个分区。

> ⚠ **执行租约挡不住这件事**。租约的键是「作业名 + 本次到期时刻」，重跑给的窗口与调度器
> 那一轮的到期时刻不同，两边各拿各的租约。挡它的只有重跑自己那道守卫。

两种处置：

1. 把 `--to` 提前到打印出来的回看起点之前（**首选**）；
2. 确认常驻 worker 此刻不在跑批，加 `--allow-overlap`。

没有任何调度节奏的作业不受这条约束——调度器根本不碰它们。**但别把这句话当成画像聚合列的通例**：
`First` / `Last` 与 `Sum` / `Count` 两族自带节奏（每日按到达主体 + 每周日全量），
重跑它们时这条守卫会生效。

## 重灌 / 重放历史数据：灌完必须对账

**同一批历史事件隔 48 小时以上再投一次，累计列会重复累加。** 去重集只保 48 小时
（`RedisStateStore.dedupeTtl`），而累加值永不过期——被重复加进去的那笔会留在基线上，
之后每一笔都在错的基线上继续加。症状只是数字偏大：不报错、不进死信，
明细表那侧还被主键去重吃掉了，于是两张表对不上（TPG-2131 就是这么发生的）。

故重灌之后按这个顺序收尾：

1. **先让流层把这一批吃完**（消费到位、攒批刷完），再跑对账——对账的修正会被在途的流层写入盖回去
   （[OPEN-ISSUES #83](../../src/backend/frameworks/materialize/OPEN-ISSUES.md)）。
2. **对受影响的目标表跑一次 reconciliation**，它同时把状态层回灌成重算值：

   ```
   --rerun
   --jobs-for-table dim_cst_profile,dim_cst_account
   --from <重灌区间起点>
   --to   <重灌区间终点>
   --mode reconciliation
   ```

3. **核一眼**：累计列与按明细重算的结果应当逐行相等。判据 SQL 见 TPG-2131 的评论。

**等常驻对账兜也可以**（每日一轮，最长偏一天），但分群、筛选、报表在这一天里读到的都是偏大的值——
重灌是计划动作，别把这一天生留给下一个人。

## 重跑不做的四件事

- **不推进调度水位**。台账里用的是单独一条时间线（后缀 `rerun`），不会让常驻调度器
  以为某条节奏已经跑过了。
- **不装摄取与调度器**。进程只跑被点名的那几条，跑完就退。
- **不改表结构**。收敛档位被强制成 `PlanOnly`：只比对、只报告，不执行任何 DDL。
  重跑可能跑在与线上不同的代码版本上（本地起一个进程连生产就是这一形态），
  那时 `Apply` 会把本地声明的差异 ALTER 到生产表上。破坏性漂移仍然让它起不来。
- **`--dry-run` 完全不启动宿主**。连 schema 比对和台账建表都不做，真的什么都不碰。

## 跑完查什么

台账（引擎自己的库，`ClaimStore` 那条连接串）按运行记行：作业名、时间线键、窗口、
写入行数、结局。排查「这段数据是哪次运行写的」从它开始。

数据本身要另外验——重跑只保证「按现在的声明算了一遍」，不保证那个声明是对的。
