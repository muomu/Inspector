## 各层说明

### 数据接入层：OpenAPI 开放平台

| 项目 | 说明 |
|------|------|
| **职责** | 统一承接外部数据写入入口，包括注册客户回调、AI 外呼结果回调、KYC 状态变更通知等 |
| **形式** | RESTful Webhook 回调 + 主动拉取接口 |
| **安全** | 签名验证（HMAC-SHA256）、IP 白名单、请求幂等键（`Idempotency-Key`） |
| **输出** | 发布事件至实时 ODS 层（.NET CAP / Kafka），事件 DTO 内嵌完整原始 Payload |

---

### ODS 层：.NET CAP + Kafka（实时 ODS）

| 项目 | 说明 |
|------|------|
| **职责** | 原始事件的发布、路由、消费与长期留档；Kafka Topic 是阶段中存储并可重放原始事件的唯一层 |
| **模型风格** | 事件 DTO 内嵌完整原始 Payload（`rawPayload` 字段），消费方可直接访问未归一化的源头数据 |
| **消息代理** | Kafka（高吞吐、持久化、支持消费者组重放） |
| **存储后端** | MySQL Storage Provider（Outbox/Inbox 表，保证 At-Least-Once 投递） |
| **Retention 策略** | **365 天**（Kafka Tiered Storage 将冷数据自动卸载至对象存储，对应用层透明） |
| **典型 Topic** | `customer.registered`、`call.completed`、`kyc.status.changed`、`deposit.received` |
| **消费端** | DWD 层写入服务、旅程编排服务、通知服务 |
| **幂等保障** | CAP Inbox 去重 + StarRocks Primary Key Upsert 幂等合并 |
| **历史重算** | Kafka 消费者组重放；365 天以内的历史补偿不需要任何 ETL |

**P1 约束：明确不做 ETL**
- DWD 写入仅保留实时事件链路（Kafka → PE.Materialize 流作业 → StarRocks，主键表覆盖写）
- 不引入任何批量 ETL 通道
- 历史补偿与重算通过 Kafka 消费者组重放完成

---

### DWD 层：StarRocks

| 项目 | 说明 |
|------|------|
| **职责** | 明细数据清洗与客户画像表，面向单客户视角的完整事实快照 |
| **核心表** | 客户画像表（Primary Key 模型，列级局部更新，现为 `dim_cst_profile`）；各业务过程事件事实表（Duplicate Key 模型，追加写入，每条事件一行不可变记录，命名格式 `dwd_{业务域}_{业务过程}_di`） |
| **写入模型** | 画像表：Primary Key 表 + 列级局部更新，多条作业各写自己的列；事实表：Duplicate Key 表，仅追加，不更新 |
| **实时链路** | Kafka → PE.Materialize 流作业（Stream Load 写出）→ StarRocks |
| **典型字段** | 注册来源、可触达标志、AI 外呼意向评分、KYC 状态、首入金时间、活跃度分层 |
| **查询用途** | 画像表为 DWS 层聚合和人工筛单提供明细快照；事实表为漏斗转化计算、时序分析和历史回溯提供原始事件序列 |

---

### DWS 层：StarRocks

| 项目 | 说明 |
|------|------|
| **职责** | 多维聚合汇总，面向运营分析、旅程指标与漏斗计算 |
| **核心表** | 每日漏斗聚合表（命名格式 `dws_{业务域}_{粒度}_1d`）、客群分层快照表（命名格式 `dws_{业务域}_{粒度}_td`） |
| **计算方式** | PE.Materialize 聚合作业：流层即时累加 + 批层定期校准（数仓里没有物化视图） |
| **典型指标** | 注册→可触达率、外呼→高潜转化率、KYC 完成率、首入金转化率、7/30 日留存率 |
| **查询用途** | 运营看板数据源；ADS 层定期同步快照 |

---

### ADS 层：Redis · MySQL · 服务内存存储

| 存储介质 | 职责 | 典型数据 |
|----------|------|----------|
| **Redis** | 高频读取缓存、实时决策结果缓存、限流计数器 | 客户分层标签快照、外呼准入判断结果、API 响应缓存 |
| **MySQL** | 运营配置持久化、看板报表快照、人工操作记录 | 规则配置表、运营人员批注、导出任务记录 |
| **服务内存存储** | 进程内热数据缓存（`IMemoryCache`）、配置预加载 | 当前有效规则集、黑白名单、枚举字典 |

**缓存刷新策略：**
- Redis：DWS 层定时任务推送 + 事件触发局部失效
- 服务内存：进程启动预热 + 滑动过期窗口（默认 5 分钟）

## 技术选型依据

| 层级 | 选型 | 核心理由 |
|------|------|----------|
| 数据接入层 | OpenAPI 开放平台 | 统一对外契约，隔离外部平台差异，便于签名验证和限流 |
| ODS | .NET CAP + Kafka | 原生 .NET 集成，Outbox/Inbox 双保障；Kafka 支持事件重放和多消费者组；Tiered Storage 实现 365 天低成本留档 |
| DWD / DWS | StarRocks | Primary Key Partial Update 支持多源并发写同一宽表列；向量化引擎满足毫秒级 OLAP 查询 |
| ADS | Redis + MySQL + 内存 | 按访问频率和持久化需求分层；Redis 负责低延迟读，MySQL 负责持久化审计，内存负责极热配置 |

## 分层职责边界

| 层 | 存储 | 职责 | 加工规则 |
|---|---|---|---|
| **ODS** | Kafka | 原始事件留档，事件 DTO 内嵌完整 Payload，Retention 365天；历史重算通过消费者组重放完成 | 不加工，原样保留 |
| **DWD** | StarRocks | 明细清洗层：原子粒度事件 + 标签宽表 | 维度退化；数据清洗；不聚合，不跨粒度合并 |
| **DWS** | StarRocks 物化视图 | 轻度汇总层：面向分析主题的公共指标 | 只聚合，不混写不同统计周期；基于 DWD 构建 |
| **ADS** | Redis + MySQL | 应用消费层：运营看板、低延迟 API | 从 DWS 推送；禁止跳过 DWS 直接从 DWD 重复加工 |

**层次调用方向（单向）**：ODS → DWD → DWS → ADS；禁止逆向引用。

## 字段命名规范

### 基本规则

所有字段名使用 `snake_case`（全小写，下划线分隔），不使用驼峰或大写。

| 字段类型 | 命名规则 | 示例 |
|---|---|---|
| 主键 | `{实体名}_id` | `customer_id`, `call_id` |
| 外键 | `{实体名}_id` | `customer_id` |
| 布尔标志 | `is_` 或 `has_` 前缀 | `is_reachable`, `has_deposited` |
| 时间戳（含时分秒，UTC） | `{动词过去时}_at` | `registered_at`, `completed_at` |
| 日期（仅年月日） | `{动词过去时}_date` | `created_date`, `partition_date` |
| 比率 | `{业务}_rate` | `kyc_completion_rate` |
| 分层/标签 | `{主题}_tier` 或 `{主题}_segment` | `activity_tier`, `ltv_segment` |
| 状态 | `{主题}_status` | `kyc_status`, `call_status` |
| 分区字段 | `partition_date` | — |

**`_at` 列存 UTC 时刻，条件里的「某一天」按租户本地日展开**：分群与客户列表把 `yyyy-MM-dd`
字面量换算成 `[本地日 00:00, 次日 00:00)` 的绝对区间再比较（夏令时那天是 23 / 25 小时）。
日边界由 `TenantCalendar` 给出，内存求值与 SQL 下推用同一份——某一侧另按 UTC 日算，就会在同一条
条件上筛出两批人。

### 字段列排列顺序

在建表 DDL 中，字段按以下顺序排列（有助于快速定位字段类型）：

```
主键 IDs → 外键 IDs → 业务字符串字段 → 度量数值字段 → 布尔标志字段 → 日期字段 → 时间戳字段 → 技术公共字段
```

### Null 值处理

| 字段场景 | 处理方式 | 原因 |
|---|---|---|
| 维度/枚举字段缺失 | 填 `-1` | 便于 GROUP BY，避免 null 分组丢失 |
| 度量/指标字段缺失 | 填 `0` | 避免 SUM/AVG 中 null 传播 |
| 标签宽表 Partial Update 字段 | 保持 `NULL` | null = 该列来源尚未写入，语义不同于"值为0" |

|---|---|---|

## 事实表设计四步法

新建 DWD 事实表时必须**按序完成**以下四步，否则不得开始建表：

### 第一步：选择业务过程

明确一个**单一的、原子的业务动作**。禁止将"注册 + 外呼 + 入金"放到同一张事实表中。

### 第二步：声明粒度

一行代表什么？必须用自然语言明确描述，例如：
- "一次客户注册事件"
- "一次 AI 外呼完成回调"
- "一次入金到账记录"

### 第三步：选择维度

- **维度退化**：常用维度属性（注册渠道、呼叫结果分类、KYC 平台）直接冗余到事实表
- **不建独立 DIM 表**（除非该维度：①跨多张事实表使用，且②变化缓慢，如国家字典、渠道字典）

### 第四步：选择事实（度量）

只选**与该业务过程直接相关**的度量。例如"外呼完成事件"的度量包括通话时长、意向评分，不包括该客户的历史入金总额（后者属于宽表聚合字段）。

## 客户级派生列的落点判据

上一节管「新建事实表」。本节管另一件事：新增一个**「一行一客户」的派生列**时，它进哪张表。

**按序答这三问再动手。**不答就写的后果是可复现的——`first_kyc_approved_at` 与 `kyc_completed_at`
是同一个概念的两种取法，一个在首事件表、一个在宽表，靠的是当时有人想清楚了；而同期的
`first_deposit_at` 只在宽表、`first_live_account_opened_at` 只在首事件表，靠的是当时没人想。

### 第一问：粒度是不是「一行一客户」？

不是 → 它属于事实表（一行一次业务动作）或指标表（一行一个统计桶），到此为止，走上一节的四步法。

### 第二问：它答的是「第一次」还是「现在」？

这是落点的**唯一判据**。两者的差别不是口味：

| 语义 | 列名 | 产出方 | 落点 |
|---|---|---|---|
| **首次态**：第一次发生在什么时候，写定后不再变 | `first_` 前缀 | `Agg.Min`（时刻列）/ `Agg.First`（值列，排序表达式必填）/ 里程碑事件投影 | `dwd_cst_customer_first_events` |
| **当前态**：现在是什么，会被后续事件改写 | 无前缀 | LWW / `Agg.Max` / 累加 / 滑窗 | `dwd_cst_label_wide` |

**时刻列用 `Agg.Min`、值列用 `Agg.First`，两者不可互换**：首笔入金**金额**取 `Agg.Min` 得到的是
「最小的那一笔」而不是「第一笔」——一个完全合法、完全错误的数字。

同一概念两种语义都要就**两列并存，这不是冗余**。现成的例子：`first_kyc_approved_at` 取 MIN
（他第一次跨过这道门是哪天——同期群统计要这个），`kyc_completed_at` 取 MAX
（现在这次通过是什么时候——证件失效后重新过审是合法路径）。

### 第三问：这个首次态列要不要**同时**在宽表放一份？

**只有一个正当理由：宽表上有搬不走的读者。**两类：

1. 前端列表页直接筛选或展示它，而查询面不能跨表 JOIN（租户谓词进不去子查询）
2. 读者在 `modules/CDP` 等旧形态模块里，而那些模块按 [AGENTS.md §4](../AGENTS.md) 不做合规重构

命中就在宽表放一份，且必须满足两条，否则不许放：

- **同源**——两处的值来自同一条作业或同一个事件，不是两份各自算一遍的实现
- **有机检**——两份口径漂了不会报错，只会让两张表的数字对不上

现成的例子：`first_deposit_at` / `first_deposit_amount` 只在画像表，因为线索面拿前者当定义谓词、
且旧形态模块有十几处在读。反面对照是**有效 FTD**：达成记录只在 `dim_cst_valid_ftd`，画像表不放一份
—— 今天它在宽表上没有读者，而上面这两条判据要的正是「有搬不走的读者」。

### 机检

`first_` 前缀与产出方双向绑定，声明期断言两条：

- 凡 `first_*` 列，产出作业必须是 `Agg.Min` / `Agg.First` / 事件投影——用 `Agg.Max` / LWW 写它，是把当前态伪装成首次态
- 凡 `Agg.Min` 作业，目标列必须叫 `first_*`，否则登记进白名单并写明理由——那是把首次态放错了名字

⚠ **这两条断言目前没有机检**：原用例 `Tradepass.Growth.Compute.Tests/FirstStateColumnTests.cs`
随旧链（`platform/compute`）2026-08-17 退役一起删了，`Customer.Compute.Tests` 里没有对应物。
它守的是「首次态别被当前态写法伪装」，新链的 `dim_cst_profile` 上 `first_*` 列有十几个——
补一条同型用例（扫本包声明的全部列）是笔小账。

## StarRocks 物理参数规范

### 表模型选型

| 场景 | StarRocks 模型 | 理由 |
|---|---|---|
| DWD 事务型事实表（不可变事件） | **Duplicate Key** | 纯追加，无 PK 索引开销，Compaction 写放大低 |
| DWD 客户标签宽表（多源更新） | **Primary Key** | 支持 Partial Update，保证主键唯一性 |
| DWS 汇总表（物化视图） | **Aggregate Key 或 Primary Key** | 根据是否需要 Upsert 决定 |

### 分区策略

**先判分不分**（见下文「分不分区」）：单日新增到不了百万行的明细表整表不分区，
下面这些粒度与约束只对**分区的**表成立。

```sql
PARTITION BY date_trunc('day', event_time)
```

- **默认日分区**：80% 查询包含时间过滤时，以天为粒度
- **小时分区**：单日数据量超过 100 GB 或 tablet 数接近上限时，降级为 `date_trunc('hour', event_time)`
- **硬性约束**：总分区数 ≤ 100,000；每分区 ≤ 100 GB；每 BE tablet 总数 ≤ 200,000

### 分桶策略

| 表类型 | 分桶键 | 理由 |
|---|---|---|
| 事件事实表 | `customer_id`（高基数，推荐） | 按客户剪枝，支持 colocate join |
| 标签宽表 | `customer_id` | 与事实表同分桶键，支持 colocate join |

```sql
-- 推荐：自动分桶（v2.5.7+）
DISTRIBUTED BY HASH(customer_id)
PROPERTIES ("enable_auto_tablet_distribution" = "true")
```

### 物化视图刷新策略（DWS 层）

> ⚠ 现网 DWS 全部由 PE.Materialize 聚合作业产出，数仓里没有物化视图；本节只在手建 MV 时参考。

| DWS 表类型 | 刷新策略 | 配置示例 |
|---|---|---|
| 日汇总（`_1d`） | 定时刷新，每天一次 | `REFRESH ASYNC EVERY (INTERVAL 1 DAY)` |
| 小时汇总（`_hh`） | 定时刷新，每小时一次 | `REFRESH ASYNC EVERY (INTERVAL 1 HOUR)` |
| 实时指标（低延迟） | 基表变更自动触发 | `REFRESH ASYNC` |
| 历史补偿 | 手动触发 | `REFRESH MANUAL` |

**最佳实践**：为物化视图指定 `PARTITION BY`，实现分区级增量刷新，避免全表重算。

## 分区生命周期

### 各层 TTL 规范

**数仓的表不设 `partition_live_number`。** 那个属性让 StarRocks 到期自动删分区——删的是真数据，
而「被删了」与「本来就没有」在报表上看不出区别。StarRocks 侧的数据**不删不搬**（2026-09-20 决策：
总量评估在几亿行量级，StarRocks 扛得住），代价是分区数只增不减。

| 层 | 表类型 | 留多久 | 谁来清 |
|---|---|---|---|
| ODS（Kafka） | 原始事件 Topic | 365 天（超期冷数据卸载至对象存储） | Kafka Retention + Tiered Storage 配置 |
| DWD | 事务型事实表 | 永久（不删不搬，2026-09-20 决策） | 不需要清 |
| DWD | 客户标签宽表（Primary Key） | 永久（一行一主体，只有最新状态） | 不需要清 |
| DWS | 日汇总（`_1d`） | 永久（历史趋势要读全段） | 不需要清 |
| DWS | 小时汇总（`_hh`） | 永久 | 同 DWD（当前本仓没有 `_hh` 表） |
| ADS（Redis） | 实时快照 | 按业务需要（7–30 天） | Redis `EXPIRE` TTL |
| ADS（MySQL） | 报表快照 | ≤ 1 年 | 定时清理脚本 |

> **别把「保留期」与引擎的「回填下界」混为一谈。** 声明里 `PartitionBy(..., backfillFloor: n)` 那个数
> 只告诉批作业「历史回填回溯到哪一天为止」（现值 720 天，同时是周兜底对账的回看窗口），
> **它不删任何数据**。此前两者共用一个数，于是想调其中一个就会动到另一个。

### 分不分区

判据是**一个分区装得下多少**，不是表有多大：一个分区至少切一个 tablet，而一个 tablet 装 1–10 GB 才划算。

| 单日新增 | 怎么分 |
|---|---|
| ≥ 百万行 | 按日（`PARTITION BY date_trunc('day', …)`） |
| 到不了百万行 | **整表不分区**。几十行一天的表切日分区，攒的是一堆几十 KB 的小块，查询要逐个打开它们 |

不分区的代价是按时间过滤收不住扫描面（排序键的前缀索引对时间范围查询不生效，真正裁扫描面的只有分区与分桶），
但这个量级上不要紧：固定开销占了绝大部分。

> **这个判断的依据是一次类比，不是分区 A/B 实测**：引擎 OPEN-ISSUES #63 那次量的是
> 「1000 万行的表换主键键序」——扫描面从 17~56 万行压到 0~2 行，单次耗时只省 1.6 ms。
> 它证明的是「在这个量级上，扫描面砍 5 个数量级也换不出毫秒」，形态是点查、两边都还分着区。
> **没有做过「同一张表分区 / 不分区」的对照实验。**

> ⚠ **建完表改不了**：StarRocks 不支持变更分区方式，判错了只能删表重建（存量数据得重灌）。

> **注意**：Expression Partitioning（v3.0+）是推荐方式，支持迟到数据写入正确的历史分区；不推荐在迟到数据场景下使用 Dynamic Partitioning（对迟到数据直接报错）。

## 数据质量要求

以下五项是**强制要求**，新建表时须同步满足：

### 1. 唯一标识符

每张 ODS/DWD 全量表（`_df` 后缀）必须指定唯一性字段（Primary Key 或业务 Unique Key），并通过数据质量任务定期检查。

### 2. 空分区告警

对**分区的** DWD 表，监控每日是否出现空分区（行数 = 0）。空分区视为数据管道断链信号，需触发告警。

> ⚠ **不分区的那些表用不了这条**（本仓 12 张 `dwd_cst_*` 里有 10 张不分区）。
> 它们的断链要靠「按 `local_date` 分组数当天行数」来看，不是靠分区元数据。

```sql
-- 参考检查语句（以某 DWD 增量事实表为例）
SELECT COUNT(*) FROM dwd_{业务域}_{业务过程}_di
WHERE partition_date = CURRENT_DATE - 1
HAVING COUNT(*) = 0;
```

### 3. 枚举字段分布监控

`kyc_status`、`call_result`、`deposit_channel` 等枚举字段，在摄取作业写入前进行白名单校验，并对枚举值分布的环比变化设置阈值告警（新增未知枚举值立即告警）。

### 4. 记录数环比监控

每日新增记录数与前7日均值的偏差超过 ±30% 时触发告警，防止上游系统静默故障导致数据漏写。

### 5. 表和字段注释强制要求

所有建表语句必须包含：
- 表级 `COMMENT`（说明业务含义和粒度）
- 所有字段 `COMMENT`（说明字段业务语义，枚举字段需列出合法值）

违反此项的建表 PR 不允许合入。

## 层次调用规范

```
ODS（Kafka）
  └→ DWD（StarRocks）         ← 实时链路：PE.Materialize 流作业
      └→ DWS（StarRocks）     ← PE.Materialize 聚合作业（流层即时 + 批层校准）
          └→ ADS（Redis/MySQL）← DWS 推送 + 事件触发失效
```

- **DWS 优先原则**：ADS 层优先消费 DWS 汇总层数据；需要 DWD 明细的场景（如漏斗溯源、原始事件重放）直接查 DWD，不建立 ADS 过渡表
- **禁止跨层聚合**：不允许 DWS 层跨越自身聚合 DWD 数据时混入 ODS 原始字段
- **任务深度限制**：从 DWD 到 DWS 的物化视图级联深度不超过 **3 层**（DWD → DWS_1d → DWS_td 为2层，合规）

## 禁止事项

| 禁止 | 说明 |
|---|---|
| 同一事实表混放不同粒度的行 | 一张事实表只有一个粒度声明 |
| DWS 层一张表混放多个统计周期 | `_1d` 和 `_td` 数据必须分表存放 |
| 合并多种事件类型到带 `event_type` 的单表 | 每种事件类型独立建表 |
| DWD 层事实表使用 Primary Key 模型（对不可变事件） | 不可变事件只用 Duplicate Key |
| ADS 层跳过 DWS 从 DWD 直接重复加工汇总数据 | 公共汇总沉淀到 DWS，ADS 只做消费 |
| 建表不写 COMMENT | 强制要求，无注释的建表不允许合入 |
| 在迟到数据场景使用 Dynamic Partitioning | 改用 Expression Partitioning |
| ODS 数据直接暴露给 ADS 消费 | 必须经过 DWD 清洗 |
